# BR1977 — a Hinglish gadiyan city game was told the kit was on disk

Scope: BR1977 only, inside the frozen audit boundary 1951..2105. Branched from `487a18336e12e6d914a86c33f6225f5027c6f6c4` (the #4169 squash-merge of exact BR1976 head `e08fd1d31`, which is origin/main at branch creation). ## Anonymous technical evidence

Account, workspace, session, build and history identifiers, exact timestamps, raw customer text and generated customer-code excerpts are intentionally omitted. The evidence JSON retains only the technical outcomes needed to explain the regression.

A 3D city-game request used the Hinglish word `gadiyan`, but the contract recorded no vehicle. Five recipes reported success while only three files were present after sandbox unavailability; the builder was incorrectly told the kit was ready. A core module was still missing shortly afterward. The resulting app had no `index.html`, a custom vehicle import arrived after the missing-file gate, and a platform touch-controls export was missing after an overwrite. The preview remained blank/404, the release gate correctly stayed RED, and the failed build was not charged.

The retained evidence is incomplete (500 of 508 timeline entries); no production replay or provider call was performed. Customer-specific project names, source bodies and log excerpts are not publication evidence.

## Root cause (F1)

`buildGameContract` already maps English `cars?` and Hinglish `gaadi` to `vehicle: 'car'`, and `gameContractBlock` then tells the builder "The player drives: a car" using the kit's `driveVehicle` / chase-camera path. This prompt never said `car`, `gaadi`, `drive` or `driving`. It said **gadiyan**. That spelling was not in `VEHICLES`, so the recorded contract had `vehicle: null` and `camera: "unspecified"`. The only world subject extracted was `building` (from "City" / "city"). Genre stayed `unknown` — correctly, this is not a racing request.

Without a vehicle in the contract the builder invented a custom vehicle module instead of using the kit vehicle, imported it before writing it, and the missing-file gate fired. The first RED blocker is that module.

## Root cause (F2)

The seed records `r.ok = !r.is_error` and then announces GAME_KIT_SEEDED whenever any recipe is ok. It does not check that the recipes wrote their files. `kitFiles` counts entries in `writtenFiles` that changed versus `writtenBeforeKit`. This build listed all five recipes as ok and only **3 files** after `SANDBOX_UNAVAILABLE`. A healthy 3D seed writes about 30 files.

Six seconds later `events.ts` was missing. The architect rebuilt a Vite project by hand and never restored `index.html`. Later, kit files that did eventually appear (`Game.ts` expecting `DEFAULT_TOUCH_BUTTONS`) were crossed with a frontend overwrite of `touchControls.ts`, producing the second RED blocker. Preview, explore, mobile-layout and playtest all failed as a consequence (404 / blank / no canvas) — they are not separate CSS or DOM bugs.

`gameKitHandoffBlock` is already honest about failed recipes ("NOT laid down — run them yourself") and silent when none succeeded. The hole was treating empty dispatcher success as success.
