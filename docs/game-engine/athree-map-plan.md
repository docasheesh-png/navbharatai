## 1. What the admin asked for (verbatim intent)

- One very large, realistic, **100% ours** map named **"Athree map"**, ready to use in any game: racing, PUBG-style battle royale, open world, whatever the user asks for.
- Realistic: trees whose leaves move, grass that sways in wind, sea with real waves, a river, a desert, sports cars / bikes / planes (not box-like), humans, animals and birds (not cartoon). "Add whatever I forgot."
- Size: 100 km or an infinite loop.
- Existing modules stay; the map is chosen **automatically** from the user's requirement.
- **Trigger:** when a user says "athree map use hona hai" / "athree map par game banao" / names Athree in any way **and the app really needs a map**, this map is used in that game.
- Take inspiration from anywhere (public techniques); the admin chose **our own implementation** (everything ours) over third-party assets.

## 3. When Athree is used — the trigger (UPDATED 2026-11-14 at the admin's order)

Athree is used when **any ONE** of these three is true:

1. **Named + needed.** The user names Athree in any way ("athree map use karo", "athree map par game banao", "a3", "a-three", Hindi/Hinglish spellings — input parsing is exempt from the English-only UI rule, like the greeting detectors) **and** the game really needs a map. → Athree, deterministically.
2. **A big map is really needed.** The app is a game or world that needs a large map — racing, open world, battle royale, flight, explore, survival, driving. Athree is then **eligible** (see the precedence rule below). It is not eligible for a calculator, a form, a dashboard, a 2D puzzle or a small single-screen level: nothing to put a map on.
3. **The librarian chooses.** The game/asset library's librarian may pick **any** suitable map or asset **at random**, Athree included. Whatever it picks is used.

**Named but not needed** (condition 1's second half fails): the answer says plainly that this app has no map to put Athree on, and what Athree would be for. Never a fake map.

### Precedence and two safety rules (written down so the three conditions cannot contradict each other)

- **Order of evaluation:** (1) a user who NAMES a different map, or says they do not want Athree, wins over everything; (2) condition 1 → Athree; (3) otherwise, if a big map is needed, the librarian picks **at random from every map that fits the request** (conditions 2 and 3 together: Athree is always in that pool, never excluded, never forced).
- **"Random" is random once, then stable.** The pick is made at the project's first build from a seed derived from the request, **stored in the project's workspace memory, and reused on every later edit.** A map that changed on every rebuild would break the user's game (spawn points, roads, saved progress). An explicit user request to change the map re-rolls it. Tests: the same project gets the same map on 10 consecutive rebuilds; two different requests can get different maps.
- **Random only among maps that fit.** A racing game is never given a flight-only airfield map; the librarian filters by profile (racing / battle-royale / open-world / flight / explore) first, then picks.

Implementation: one pure function `athreeMapIntent(prompt, genre, stored)` → `{ use, reason, via: 'named' | 'needed' | 'librarian' | 'none' }` in the style of `buildConfirmation.ts`, plus the library's existing selection for the random pick; the architect prompt and the tool dispatcher both read the same result.

## 4. Architecture

New folder `src/server/lib/athreeMap/` of **pure generators** (the existing recipe pattern): each returns `{ files, dependencies, instructions }`, is wired once through `GAME_RECIPES`, `ToolCatalog`, `ToolDispatcher`, the architect prompt, `AppKnowledgeBase`, `gameKitHistory` and the census tests, and is listed in the game library under category **`maps`** with `license: owner-provided (NavBharatAI own work)`.

The generated game code talks to one small, stable API (so racing, battle-royale, tycoon, physics and the library never depend on internals):

```
AthreeMap.create({ seed, profile, quality })
  .heightAt(x, z)  .normalAt(x, z)  .biomeAt(x, z)  .waterLevel
  .roads            // splines: id, points, width, type
  .spawnPoints(kind)// player / vehicle / plane / boat / animal
  .windAt(x, z, t)  // ONE wind field shared by grass, trees, water, clouds
  .update(cameraPos, dt)  // streams chunks in/out, floating origin
  .dispose()
```

- **Seeded & deterministic**: same seed → same world (tested).
- **Streaming chunks** around the camera; **floating origin** so float precision never breaks at 50 km from zero.
- **Infinite loop** = periodic noise (tileable with a period, e.g. 100 km), so the world wraps seamlessly; **bounded** worlds (arena, region) use the same code with a falloff to sea.
- **One height function** feeds both the renderer and the Rapier heightfield colliders (the physics module from stages A/B), so what you see is what you drive/walk on.
- **Profiles**: `racing` (closed circuit + long roads), `battle-royale` (island arena ~8×8 km with points of interest, hooks for the existing battle-royale core), `open-world` (region / infinite), `flight` (airfields, long runways), `explore`.
- **Quality tiers** `phone | mid | desktop`: view distance, grass density, tree LOD distances, water mesh/FFT size, shadow resolution, chunk size — every number in one table, with a **frame budget test** (triangles and draw calls per tier).

## 8. Honest ceilings and risks

- **What our own code can reach:** terrain, water, grass, trees, sky, desert, roads — *very good* (shader-level realism). Vehicles and aircraft — *good, believable, PBR*, not scanned-model detail. Birds, animals — *believable at distance, game-like up close.* Humans — *the weakest part*; photoreal faces and clothing need scanned assets, which are outside "100% ours" unless the admin later buys/approves them. The asset slot stays open for that.
- **Phone performance cannot be measured here.** Only budgets (triangles, draw calls, instance counts) are tested; real frame rate needs the admin's device. Tiers are conservative on purpose.
- **"Infinite"** means a seamless periodic loop plus streaming, not unbounded memory.
- **Scope:** this is many sessions of work. No time promise is made; each phase reports what it proved and what it did not.
- **Open items elsewhere** (not blocked by this plan, not forgotten): Q-2662 render proof needs a real sandbox; Q-2664 Code Studio preview; Q-2667 needs the next upload failure line; GitHub Actions not starting jobs on the admin's account (APK builds depend on it).
