# Pro builder Surplus integration (default OFF)

This is a real, mocked-tested native tool-loop integration, not the text-only helper. It is not activated, funded, credential-tested, or deployed. No production reviews or pilot budget are seeded by this change.

## Scope and operation

`AGENTV3_SURPLUS_BUILDER` defaults false. OFF does no new database, metadata, inference, or receipt work and preserves the existing tier ladders and monetary formulas. Standalone Free Chat, Doctor and image generation are untouched. The multiplexed Pro chat resolves non-build conversation using its existing route. Pre-intent classification and image/vision interpretation remain existing services, outside the discounted build-inference claim. Images and VM/hosting are not advertised as 90%-discounted.

After actual build intent is established, the session preflights before the Weak scope classifier and sandbox. Weak classification uses the existing fixed GLM classifier, strict parser, eight-token limit and five-second deadline. A dedicated policy assertion allows only that client without enabling other legacy builders; canary, gateway and strict-free fences still apply. Measured classifier usage enters the GLM ledger and redacted scope audit, including rejected classifications. Classifier failures cannot poison the Surplus coding session or trigger coding recovery. This separation does not fix or bypass a Surplus reservation failure. Fast/plan/main/heal/escalation/retry runners share the session. Its winning model remains sticky from the configured universe of up to 15 candidates, after independent coding-quality, capability, privacy and price-floor filters; fresh eligibility is checked on every dispatch. A cheaper model appearing later alone does not change the build model. Only the bounded safe failed-turn fallback below may select the next cheapest eligible model, which then becomes sticky. Existing Weak model prohibitions remain.

Native history, tool schemas, parallel tool calls/IDs/results, output-limit status and Stop are preserved. Model requests across the build's runners are queued serially to respect the conservative one-pending-call pilot fence; parallel tool execution remains supported. Queued calls honor deadlines and cancellation. Across different builds sharing one pilot authority, a concurrent pending call causes an honest busy refusal; this initial pilot is globally serial, not a claim of provider concurrency capacity. Unadapted legacy text/tool auxiliary calls inside the admitted build are refused by the scoped legacy boundary, never silently used as paid fallback. Such a blocked auxiliary step is a limitation, not a claim the auxiliary task ran.

Transport sends only the fixed `https://api.surplusintelligence.ai/min90/v1/chat/completions` endpoint with locally validated top-level `provider` and `si_route: { objective: "price" }`. SDK retries, redirect following, arbitrary endpoints and implicit fallback keys are not used. Provider model/family and marketplace rail are checked in fast response headers or long-response `surplus` metadata. Unknown/adapted protocol parameters fail closed. An offer ID is observed price-generation evidence, NOT a claim the wire can pin an individual offer.

Sources: https://www.surplusintelligence.ai/docs/marketplace/routing-controls and https://www.surplusintelligence.ai/docs/reference/long-running-responses . Price observations are estimates, not guaranteed quotes or invoices. The separate reviewed request-time-floor contract permits a bounded cached observation with unknown origin-generation time; it never invents that timestamp. The strict metadata-only preview still blocks that case.

## Required independent reviews

Server-only fixed document `live_ai_registry/surplus-builder-reviews` has a positive integer `revision`. It supplies:

- Account ID bound to SHA-256 of the exact current server credential, account/privacy review expiry, marketplace-only/no fallback-key review and a live-credential-check review. No key is stored in the document.
- Explicit pilot ID/expiry, maximum calls, maximum estimated micro-USD budget, separately reviewed provider/account spending limit expiry, and no-auto-top-up approval. There are NO authorized defaults. A user must approve the actual pilot budget before anyone configures this.
- Reviewed `/min90` request-time floor and exact provider pin contract.
- Comparable model+provider coding benchmark review, artifact hash and expiry; exact-offer-only review cannot authorize a provider-family pin.
- Model capability, context/output limits, native and parallel tool/history checks, returned identity and canonical-charge contract checks.
- Exact official model/version tariff snapshot and a linked reviewed usage mapping. Unknown cache/reasoning/fee dimensions are not zero. Marketplace reference prices never become the official billing ceiling.

Refresh and metadata observations alone cannot create/renew these approvals. Every permitted request retains its immutable reviewed account/model/tariff snapshot. The current review revision/account/pilot is checked transactionally again while reserving, and freshness/credential checks repeat before physical HTTP. The manager control revision and disabled-model list are rechecked in the reservation transaction, so a concurrent admin exclusion cannot silently dispatch an old authorized permit. No request body accepts reviews.

## Pilot and receipt accounting

Before HTTP, a Firestore transaction reserves a unique pending attempt under the account+credential-generation+pilot identity and records a content-free per-call audit row. It limits calls and cumulative actual-plus-estimated-reservation spend. The reservation is explicitly an estimate, NOT a provider hard spend cap. A changed/revoked review or failed reservation means no HTTP. The pilot may span apps within its explicit bounds; each receipt binds its own build ID.

A timeout, interrupted body or unknown outcome keeps its pending liability and blocks later pilot calls. No automatic refund/retry/reset is invented. Since the provider exposes no validated idempotency contract here, exactly-once physical inference is NOT claimed. Known responses persist exact normalized usage, provider-reported canonical charge, policy/version/price generation and the accounting decision. Late completed responses after Stop retain expense but cannot execute tools/publish output. Invoice reconciliation remains explicitly `not-reconciled`. After recording expense, an actual charge above its reserved estimate, realized savings below90% against the validated same-usage official tariff, or unavailable comparison quarantines further pilot dispatch. The reason persists across restart and Stop/duplicate callbacks; there is no automatic recovery. A separately reviewed recovery/new pilot authority is required. This cannot prevent the first unexpected charge and does not erase supplier expense or rewrite the capped user charge. Exactly90% passes the exact-decimal comparison.

Only this Surplus build share uses `min(10 × validated actual Surplus inference cost, reviewed official same-model/same-usage tariff)`. Decimal arithmetic is exact through receipt aggregation; conversion to the existing numeric wallet currency boundary happens last. Legacy inference and VM keep their existing calculation and are not multiplied again. The existing wallet remains the only monetary writer and its idempotent build reference and failure/preview/Stop rules remain intact. Missing receipt, usage or tariff evidence blocks settlement and further calls rather than using zero or generic Sonnet rates. A discarded/partial/barren call with one total supplier charge is absorbed in full; its supplier expense is retained.

`surplus_build_receipts` and `surplus_pilot_admissions` are server-only retained financial/audit fences, explicitly classified in DataRetentionManager. No prompts, code, raw provider bodies or secrets are stored. Pilot call limits bound receipt growth. Automatic expiry deletion would erase liability/re-arm a pilot, so none is installed. Reconciliation/archive requires separate authorization. Serialized records are audit data, not inference or wallet authority.

## Validation and activation

Mocked tests exercise real production-adapter wiring, exact policy decisions, route settlement partitioning, durable transactions, concurrent queueing and legacy isolation. They do not prove a real account's tool quality, current rates, provider identity or credential behavior. Activation still requires independently reviewed evidence, explicit budget approval, a separately authorized bounded credential test, final review and deployment authorization. This patch performs none of those operations.

## End-user white-label boundary

Public messages, error codes, SSE and saved chat never identify the upstream route or expose supplier prices/review reasons. Legacy provider-debug flags cannot append provider/model tags to public replies. Raw identities and receipt evidence stay in authenticated admin diagnostics. User report projection remains allow-listed; raw client reads of internal AI usage records are denied in the reviewed rules patch, while the authenticated wallet-log projection remains available. This code-only rule change affects permissions when deployed: Cloud Build automatically deploys Firestore rules, so merge/deployment requires separate explicit approval. No live rules were changed here. Legally required privacy/subprocessor disclosures and truthful product/foundation-model attribution are not removed.

The preflight workload calculation is a one-call affordability signal, not a complete multi-turn build quote. Public refusals omit unqualified estimate amounts for this path and explicitly explain usage-based charging; legacy provider projections are unchanged. No new wallet hold or fixed-price promise is introduced. Existing atomic wallet debit/floor and failure/preview exclusions still bound the amount actually charged; the explicit durable pilot authority and per-turn budget controls separately constrain supplier spend. A provider can charge more than an estimate on the first affected request, which is why post-receipt quarantine is not a prevention guarantee.

The Surplus native runner uses a truthful service-identity instruction and a bounded guard on complete non-streamed narrative for explicit platform self-identification/routing disclosures. Its canonical narrative text is projected consistently for callbacks and saved chat, while tool arguments, generated files, fenced source and legitimate integration discussion are preserved. This is a scoped defense, not a guarantee against every possible model-generated phrase. It does not claim NavBharatAI trained the underlying foundation model.

## Bounded silent failed-turn fallback

There are at most three physical attempts per native turn under one overall deadline. Each attempt has a fresh permit and durable reservation, identical original conversation/tool definitions, and its own audit/receipt. Failed attempts never enter the canonical transcript or publish text/tool callbacks. A winning fallback becomes the model used by subsequent turns; the same-model price/provider candidate is still refreshed. No direct-provider/legacy or less-than-90%-eligible fallback is allowed. New candidates without independent reviews remain unavailable, regardless of their catalog rank or price.

The current affirmative fallback cases are deliberately narrow:
- A documented HTTP404 `minimum_discount_not_met` or `no_sellers_for_model`, with a valid trace request ID and no contradictory usage/attempt/route evidence. The exact explicit exclusion is recorded durably as `not_attempted`, consuming an attempt but releasing its estimated hold. This is not a fabricated zero-usage supplier receipt. A generic404, request-log404, `no_healthy_sellers`, arbitrary503 or absent cost is never such evidence.
- A completed, identity-verified empty `stop` completion with fully validated supplier cost and same-usage tariff, absorbed as a whole failed call, and a durable transaction confirming no quarantine. Its real supplier expense remains recorded before selecting another model.

Unknown transport outcomes, Stop/abort, deadline/timeout, maintenance, shared-key quota/auth failures, policy filtering, malformed/identity-mismatched answers, missing accounting or quarantined pilots do not automatically retry. An uncertain timeout needs reconciliation, not optimistic replay; the inference API does not provide a validated idempotency guarantee. Canonical error cost is retained even when long-running errors put route metadata under `data.surplus`. Shared credential rate limits cannot be avoided by trying 15 models. Public wording stays generic; actual attempts/reasons remain truthful server/admin records.

Official evidence: https://www.surplusintelligence.ai/docs/marketplace/minimum-discount-routing , https://www.surplusintelligence.ai/llms.txt , https://www.surplusintelligence.ai/docs/reference/long-running-responses . Current error handling depends on documented machine codes, not message substring guesses.

## Safe runtime credential setup

Use a buyer Standard key through `SURPLUS_API_KEY`, ideally a pinned Secret Manager version mapped to that environment name. Do not use a Provisioning `inf_admin_` control-plane key: builder preflight rejects it. This code neither creates nor configures a key. Adding a key does not create account/privacy/quality/tariff/pilot approval and does not enable the builder. Keep `AGENTV3_SURPLUS_BUILDER=false` until a separately authorized reviewed test and activation. Existing Cloud Build uses `--update-env-vars` and no secret-replacement flag, so unrelated configured secret mappings and flags survive release; no deploy configuration was changed for this feature.

## Admin-only connection checks with production routing OFF

The paid registry panel provides two distinct operations. “Check saved credential” makes only the fixed authenticated `GET /v1/buyer/me` request from Cloud Run using its existing Standard key. An accepted JSON HTTP response establishes endpoint authentication acceptance only, not model access, available funds, coding quality or budget protection. The response body is discarded; account balances, keys and raw errors are never returned. This check does not require the paid-test review, and cannot unlock it.

“Test connection” is a separate lifetime one-shot: fixed primary model, fixed synthetic request for `OK`, 32 maximum output tokens, no tools, no retry and a 60-second deadline. Both production flags must remain explicitly OFF. The server durably consumes its attempt before HTTP, rechecks the exact credential/configuration and review immediately before dispatch, and never rearms the fence after a timeout, key rotation, new review or lost browser response. Cached status can be read safely. Canonical reported cost is retained even for a failed response; missing/conflicting cost remains an unknown-liability hold. A successful response is connection evidence only, never a quality approval.

The owner's maximum authorization is $1 USD for this synthetic test. The paid operation remains unavailable until independently verified provider-side budget evidence covers the current account/key and this test. Standard-key profile authentication, the reserved `preferences.limits` field, token estimates and available balance are not this evidence. No review is seeded, no HTTP caller can create it, and no endpoint changes budgets or credentials. The server-only `surplus_connection_tests` lifetime record is retained as a financial/audit fence rather than automatically deleted. Actual provider hard-stop semantics and the current configured cap must be verified before populating the review; its schema alone proves nothing.

The owner reported the runtime key/base URL and both OFF flags configured on 2026-10-24. This is not independent verification. No live credential request or paid response test was performed during implementation.

For the current paid-test review contract, an authorized reviewer must inspect the actual monthly provider budget, its active/unpaused `hard_stop:true` setting, configured limit, reported spend and exact remaining amount (positive and at most $1), and confirm that its reset is outside the entire test window. A fresh account-bound review must also establish that automatic funding/recharge is OFF, so the test cannot trigger a larger wallet top-up; absent, enabled, expired or mismatched evidence blocks only the paid operation. No funding setting is changed by this code. The review must bind the runtime credential fingerprint to the actual account/key and enclosing workspace/member scope, not an unrelated budget. Record the official source, evidence hash, reviewer and bounded observation/expiry times in `live_ai_registry/surplus-connection-test-review`. These are normalized internal review fields, not an invented provider API response schema. A screenshot may support independent manual review but does not automatically create machine authority. The code does not assume that ordinary provider budget controls mathematically eliminate every settlement risk; if trustworthy binding or a reasonable spending bound cannot be established, leave the paid test blocked and use only the authentication check. A profile-read403 is permission-limited/unknown, not proof the key is invalid.
